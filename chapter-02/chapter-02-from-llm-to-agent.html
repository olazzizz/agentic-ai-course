2.1 Definitions: workflow vs agent

The one distinction to keep: who decides the next step?

  • Workflow: your code decides. The model is called at fixed points to do a bounded job (extract, classify, draft).
  • Agent: the model decides, at runtime, which tool to call next and when to stop. Your code runs the loop and enforces limits.

Autonomy is a spectrum, and each rung up trades predictability for flexibility:

Level Who chooses the path Example Governance needed
0. Single call Nobody (one step) Summarise a ticket Output review
1. Chain Code Extract fields → validate → draft reply Tests per step
2. Router Model picks a branch, code executes it Route a request to billing / tech / sales flow Routing evals
3. Tool loop Model picks tools and when to stop “Find why this deployment is failing” Step, cost and permission limits
4. Long-running agent Model, with memory and triggers On-call assistant acting on alerts Approvals, audit, rollback
5. Multi-agent Several models delegating to each other Research team of specialists (Chapter 6) All of the above, plus inter-agent trust

Most enterprise value today sits at levels 1 to 3. Level 3 is what people usually mean by “an agent”, and it is what you build in Lab 2.

Workflow Agent
Pros Predictable; cheap; low latency; easy to test and audit; failures are local Handles open-ended tasks with an unknown number of steps; less code for messy problems; can recover from surprises
Cons Brittle: every branch must be foreseen; new cases need new code Non-deterministic; cost and latency multiply with the loop; hard to test; errors compound across steps
Best when You can write the steps down You cannot know the steps in advance

Architect’s lens: “agentic” is a design choice per step, not a product category. A good solution is usually a workflow with one or two agentic steps inside it.

2.2 The agent loop

Every step re-sends the whole growing context (Chapter 1.4): a loop’s cost grows faster than its length.

ReAct (Reason + Act, Yao et al., 2022) is the idea behind this loop: the model interleaves a thought, an action, and the observation of that action. Today’s APIs implement it natively: the model returns a structured tool_calls field instead of you parsing “Action:” text.

Stop conditions. A loop that only stops when the model feels done will eventually not stop. Every agent needs several:

Stop condition Protects against Note
Model returns no tool call Nothing: the happy path The only “success” stop
Max steps Runaway loops Hard limit, always on
Token / cost budget Bill shock Per run, not per month
Repeated identical call Stuck loops Return an error message, do not just abort
Wall-clock timeout Hung tools, slow models Essential for user-facing agents
Human approval refused Unsafe actions Chapter 12

Two design rules from the loop:

  1. Tool errors are observations, not exceptions. A failing tool returns text the model can act on (“file not found, call read_file(‘.’) to list files”). Crashing the loop wastes the run.
  2. The model proposes, your code disposes. The model never executes anything. Validation, permissions and sandboxing live in the harness.

2.3 Core building blocks

An agent is a model plus a harness. The model is a swappable endpoint; the harness is the software you host, secure, observe and pay to operate.

Block Job Key design decision Typical failure
Model Reasoning and tool selection Size vs reliability vs cost; tool-calling quality Small models pick wrong tools or emit bad arguments
Instructions Role, rules, output format Short and testable; stable text first (prompt caching) Contradictory or bloated prompts
Tools The agent’s hands and eyes Few, well-scoped, well-described (Chapter 3) Vague descriptions, too many tools
Memory / state What the agent knows now and later What stays in context vs external store (Chapter 5) Context bloat; forgotten constraints
Guardrails Limits on inputs, outputs and actions Where to block, where to ask a human (Chapter 12) Enforced in the prompt only, so bypassable
Orchestration Loop, control flow, retries, hand-offs Code you own vs a framework (Chapter 4) Hidden control flow nobody can debug

Architect’s lens: the model is the part customers ask about; the harness is the part that decides whether the solution is secure and affordable. Put your design effort there.

2.4 Patterns

Start from the simplest pattern that could work, and move down the table only when a simpler one demonstrably fails.

Pattern How it works Pros Cons / risks Cost and latency
Prompt chaining Fixed sequence; each call feeds the next, code gates between steps Simple, testable, debuggable Rigid; errors propagate down the chain Low, linear in steps
Routing A classifier call selects a specialised path Specialised prompts; cheap models for easy cases Misrouting is silent; needs its own evals Low; one extra call
Parallelization Run independent calls at once (split work, or vote for confidence) Lower latency; voting improves reliability Total tokens rise; results must be merged Same latency as one call, higher tokens
Orchestrator-workers A model decomposes the task and delegates subtasks to workers Handles tasks whose subtasks are unknown upfront Orchestrator is a single point of failure; heavy context passing High
Evaluator-optimizer One call produces, another critiques, repeat until good Quality gains where criteria are clear Loops without a good stop rule; the judge shares the generator’s blind spots High, multiplies per round
Plan-and-execute Plan first, then execute steps, replan on failure Fewer reasoning tokens per step; plan is reviewable by a human Stale plans; over-planning easy tasks Medium; front-loaded
Reflection The agent critiques its own draft or trajectory and retries Catches some errors cheaply Can talk itself into a wrong answer; weak without an external check (test, tool result) Medium to high

The first five are the workflow patterns from Anthropic’s Building effective agents; plan-and-execute and reflection are common agent-side patterns. Reflection with an external signal (a failing test, a validator) is far more reliable than reflection alone.

Choosing quickly:

  • Steps known and fixed → chain
  • Inputs fall into distinct categories → router
  • Independent sub-tasks → parallelization
  • Steps unknown but tools are few → tool loop (Lab 2)
  • Steps unknown and the task is large → orchestrator-workers or plan-and-execute
  • Output quality is checkable → add evaluator-optimizer or reflection on top

2.5 When NOT to use agents

Run the five-question test. A “no” to any question pushes you back towards a workflow.

  1. Is the path genuinely unknown in advance? (If you can draw the flowchart, draw it in code.)
  2. Is a wrong intermediate step recoverable, or reversible?
  3. Is the value of a completed task greater than its cost, including the loop multiplier?
  4. Can success be checked automatically (evals, validators)? If not, you cannot improve it.
  5. Is the blast radius bounded by permissions (read-only, sandbox, small spend limit)?

Red flags to raise with a customer:

  • Deterministic problem (calculation, lookup, format conversion): a normal program is cheaper and always right.
  • Hard latency or cost ceiling: a five-step loop is 5 to 20 seconds and several times the tokens.
  • High-blast-radius actions (payments, production changes, customer-facing messages): keep a human approval gate or do not automate.
  • “We want an agent” with no task: ask what decision or workflow it replaces.

Customer-conversation phrasing: “Let’s start with the simplest design that meets your goal, measure it, and add autonomy only where the measurements justify it.”

Check yourself

  1. Give one example of the same use case built as a workflow and as an agent, and say what breaks first in each.
  2. Your loop has no max-steps guard and a tool that sometimes returns an unhelpful error. What happens, and what does it cost?
  3. Why is “tell the model in the prompt not to delete files” not a guardrail?
  4. A customer wants an agent to convert 5,000 invoices from XML to JSON. Which level of autonomy do you recommend?
  5. Which patterns from 2.4 let a human review the work before any action is taken?
Answers
  1. Example: refund requests. Workflow: classify → look up order → apply policy → draft reply; breaks first on unforeseen request types. Agent: model picks lookups and actions; breaks first on wrong tool choice, looping or cost.
  2. The model retries the failing call, each iteration re-sending the growing context, until something external stops it (rate limit, timeout, your budget). Cost grows roughly quadratically with steps.
  3. A prompt is a request the model may ignore or be talked out of. A guardrail is enforced in code (permissions, sandbox, approval gate) that the model cannot bypass.
  4. Level 0 or 1, and mostly no model at all: it is a deterministic transformation. Use a model only for the messy exceptions.
  5. Plan-and-execute (approve the plan), and any pattern with an approval gate before the action step (Chapter 12).

Lab 2: An agent loop from scratch

Time: ~3 h · Cost: about $0.01 to $0.10 with a hosted model; $0 local Goal: run, break and measure a ~100-line agent loop, then compare it with the same task as a fixed workflow.

Which model to use

This lab needs reliable tool calling. Recommended: the hosted profile with a cheap tool-capable model (from Lab 1: bash ../lab-env/labenv.sh models --tools --structured --limit 15). The whole task set is roughly 6 tasks × 2 to 4 steps × ~1.5k tokens, so a few cents.

The local profile works too, but small CPU models are slow (you saw 60 to 180 s per prompt in Lab 1) and often mishandle tool calls; a tool loop multiplies that latency by the number of steps. If you use it, choose a tool-capable model (for example qwen3:8b) and expect to wait.

Step 1: Set up

Unzip this package into the same ~/agentic-labs as before, then:

cd ~/agentic-labs/lab02
cp .env.example .env          # or copy lab01/.env and add the "Agent guards" block
uv sync

Fill in HOSTED_* (and LOCAL_* if you want the local run). .env is never committed.

Step 2: Read the code first (15 min)

Open agent.py and find, in order: the two tools and their JSON schemas; execute() (errors become text); run_agent() (the loop, with numbered guards); grade() (simple checks on the answer). Map each part to the diagram in 2.2.

Note the security choices: the calculator parses arithmetic with ast instead of eval(), and read_file resolves the path and refuses anything outside sandbox/.

Step 3: Run one task, read the trace

uv run agent.py "Read q1_sales.txt. What was total Q1 revenue and the average monthly revenue?"

Every step prints as it happens and is also written to logs/*.jsonl. Identify: how many model calls, which tools, and where tokens went.

Step 4: Run the task set

uv run agent.py --tasks tasks.json

The six tasks in tasks.json are deliberately different: no tool needed, read then compute, two files, a missing file, and a sandbox escape attempt. You get a pass/fail per task, steps, tokens and cost, plus results-hosted.csv.

Step 5: Break it on purpose (the real lesson)

Change one thing at a time, rerun, and note what changed in steps, cost and pass rate:

Experiment Change What to observe
A --max-steps 2 Which tasks now fail, and with what stop reason
B --max-tokens 1500 The budget guard firing; compare with A
C In TOOLS, make the read_file description vague (“Reads stuff”) Wrong or missing tool calls
D In SYSTEM, delete the “never do arithmetic in your head” rule Does the model still use the calculator? Are answers still right?
E Remove the repeated-call check in execute(); add a task the model cannot solve How it loops until max_steps
F --profile local (if configured) Steps, latency and pass rate vs hosted

Step 6: The same task as a workflow

uv run workflow.py

workflow.py solves the Q1-revenue task with one model call and code for everything else. Compare it with the agent’s run of one-file-two-calcs.

Deliverable: a one-page report

Answer in your own words, with numbers from your runs:

  1. Cost and steps for workflow vs agent on the Q1 task. What is the ratio?
  2. What did the agent do that the workflow could not (look at the no-tool, missing-file and escape-sandbox tasks)?
  3. What does the max-steps guard cost you (experiment A), and why do you still need it?
  4. Which single experiment (A to F) hurt most, and what design rule does it teach?
  5. Apply the five-question test from 2.5 to the Q1 task: agent or workflow? Defend it in three sentences.

Troubleshooting

Symptom Likely cause Fix
Model answers but never calls a tool Model or provider does not support tool calling Pick one with labenv.sh models --tools; check the provider’s model page
HTTP 400 mentioning tool_calls or temperature Provider rejects a parameter Set TEMPERATURE= (empty) in .env; try another model
Arguments are not valid JSON Small model The loop returns an error and the model may recover; if not, use a larger model
Local run takes minutes per step CPU inference Use hosted for this lab; keep local for the comparison in experiment F
Profile 'hosted' is not configured Empty HOSTED_BASE_URL or HOSTED_MODEL Fill both in .env
Task set passes on one run, fails on the next Non-determinism Run 3 times and record the pass rate; this is exactly what Chapter 11 formalises
